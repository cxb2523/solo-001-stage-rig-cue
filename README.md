# 舞台吊杆 Cue 预演台

零依赖（仅 Node 20 标准库），前端为原生 HTML/JS，不引任何框架。

## 运行

```bash
node --test          # 全部测试
node src/server.js   # 启动服务，默认 http://localhost:3000
```

页面加载 `data/rig.json`（12 根吊杆台账）与 `data/cues.json`（8 条 Cue），
在时间轴上拖动 Cue 调整顺序后，所有时间点、载荷曲线、冲突与等待时间会整体重算；
点「预演」画面随时间轴播放，跑完在「预演汇总」中给出冲突清单与等待最久的吊杆，
「逐步计算过程」列出每一步的数值以便核对。存在超载段落时「提交预演」按钮被禁用。

## 计算模型

- **运动**：每根杆独立设置起止高度、速度、加减速时间，按梯形速度曲线
  （加速→匀速→减速）运动；距离不足以加到额定速度时退化为三角形曲线。
- **载荷**：静态净载荷 `|吊挂 - 配重|`；加/减速段叠加动载 `吊挂 × a / g`（g=9.81，
  保守取加减速同值）；任意时刻净载荷超过额定载荷即判超载，时间轴对应段染红，
  冲突按 Cue+吊杆 合并并标注峰值时刻。
- **确定性**：计算内核 `src/model.js` 为纯函数（无随机、无时钟），同一份 Cue 表
  连算两次，载荷曲线与冲突清单逐字节一致（有测试保障）。前后端共用同一份
  `model.js`，页面上的结果与后端/测试完全一致。

## 联动组策略的取舍

联动（linked）组内多根杆必须**同时到位**，有两种常见做法：

1. **同一速度**：全组按同一个速度走，到位时间天然一致，但速度只能取各杆
   机电上限的最小值，且各杆行程不同意味着有人空转慢速、效率最低。
2. **各走各的速度、终点对齐（本项目采用）**：每根杆按自己设定的速度/加减速
   运行，组时长取各杆运动时间的最大值，用时短的杆**延迟出发**、与最慢杆
   同时到位；最慢的那根标记为「拖后腿」，快杆的延迟记为它的等待时间。

选方案 2 的理由：

- 每根杆的速度/加速度都不超过自己的设定值，不会为了对齐而被迫超速，
  安全校核（载荷曲线）可以按各杆真实运动逐段计算；
- 「谁慢谁拖后腿、谁等谁」可以精确归属到具体杆和具体秒数，正是汇总里
  「等待最久的吊杆」需要的数据；方案 1 的等待被摊薄在全组，无法定位瓶颈；
- 代价是各杆出发时刻不同，需要操作员理解「延迟出发」而非「同时启动」，
  这一点在时间轴和逐步计算日志里都有明示。

## 样例数据中埋入的缺陷（用于验收）

- `C3`：B5（二道幕杆）急升，加减速 0.5s，加速段净载荷 ≈222.8kg > 额定 150kg —— 超载；
- `C6`：B9（天幕灯杆）急降，加减速 0.4s，加减速段净载荷 ≈216.8kg > 额定 160kg —— 超载；
- `C5`：联动组中 B4 速度 0.35m/s，远低于同组的 0.8m/s —— 联动速度不同步，B4 拖后腿。

## 目录结构

```
data/rig.json    吊杆台账（额定载荷、吊挂、配重、初始高度）
data/cues.json   Cue 表（分组、联动标记、每杆起止/速度/加减速）
src/model.js     计算内核（Node 与浏览器共用）
src/server.js    静态文件 + /api/data 服务
public/          前端（剖面画布、时间轴、汇总）
test/            node --test 测试
```
